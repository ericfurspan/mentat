# This repository

*Read by agents. For people: `README.md`.*

This repository is Mentat itself: a Claude Code plugin (`.claude-plugin/`), its workflow rules (`rules.md`, loaded at session start by `hooks/session-start`), its skills (`skills/`, one per workflow step, named from `rules.md`), its builder and plan-checker subagents (`agents/`), the git hooks for agents' git (`git-hooks/`) and the `mentat` command (`bin/mentat` and `lib/`). The marketplace (`.claude-plugin/marketplace.json`) also serves opt-in modules from `plugins/<module>/`, and the committed `.claude/settings.json` turns on `mentat-reviewers` and `mentat-public-text`; this repository's Linear backlog and the grill need `mentat-linear` and `mentat-lead` on at user scope. Mentat is on here through the maintainer's user-scope install, so sessions in this repository follow `rules.md`.

- The one test command is `tests/run`. CI runs the test command on every pull request (GitHub Actions, macOS). Run it once with its output saved to a file and read the last line ("All checks passed" or "N check(s) failed"). It also runs locally on macOS.
- The external backlog is the Linear project `Mentat`, in team `Work`.
- Working files (plans, audits, trial kits) go in `work/`, which git ignores; finished ones move to `work/done/`. Nothing there is part of the plugin.
- Every file here is Mentat's own. This repository's own choices, which Mentat inherits like any other: a session merges its own ready pull request here as `MENTAT_AGENT_MERGE`, on in the committed `.claude/settings.json`, allows (`merge.md` in `mentat:review`'s folder), and the maintainer merges every other one, including any that changes a path `MENTAT_MERGE_WAIT_PATHS` lists there, such as the release pull request below (the agent account cannot approve its own pull requests).
- Keep scripts plain bash that also runs on macOS's bash 3.2.
- A setting the user switches keeps the same key in every configuration; only its value changes.
- `CHANGELOG.md` follows Keep a Changelog 1.1.0, and only a release pull request edits it: until 1.0 the existing entries stay under `## [Unreleased]` as they are, and once 1.0 exists `## [Unreleased]` stays empty between releases. For each release a session prepares one pull request that writes the new version's `## [x.y.z] - YYYY-MM-DD` section from the titles of the pull requests merged since the previous version (for 1.0, the existing entries plus the titles merged since 2026-11-08), merging, omitting and rewording titles so the section reads as a summary for users. That pull request merges last before the tag; the maintainer merges it and creates the tag, and a session never does either. Compare links at the foot use the tags from `v1.0.0` on, added once the first tag exists.
- Weigh a change to Mentat as `skills/propose/decisions.md` says a recommendation rests, whether the idea comes from a real session or from others' work, and keep it simple to describe.
- A choice here that is hard to reverse, surprising without context and a real trade-off gets a decision record in `docs/adr/`, in the same pull request: the next `NNNN-slug.md`, a title and one to three sentences of context, decision and why, as [Matt Pocock's ADR format](https://github.com/mattpocock/skills/blob/main/skills/engineering/domain-modeling/ADR-FORMAT.md) gives. A pull request that reverses one adds a new record and marks the old one superseded. Before changing a rule, read its record if it has one. Records are public: `skills/backlog/records.md` applies.
- After any pull request merges here, whoever merges it, run `claude plugin marketplace update mentat`, `claude plugin update mentat@mentat --scope user` and, for each installed module, `claude plugin update <module>@mentat` at its scope (`--scope project` for `mentat-reviewers` and `mentat-public-text`, `--scope user` for `mentat-linear` and `mentat-lead`), so the next session here loads the merged plugin and modules. The maintainer gave standing permission for these commands. A running session keeps the version it loaded until it restarts. Other checkouts update whenever they next update their plugins; nothing here depends on it.

## Code Review Rules
- The requirements are in the pull request description and any linked issue. Flag code that does not do what they say, or a test result that does not match the final commit.
- Flag any secret, token or credential added to the repository, including in tests, fixtures and workflow files. Placeholder values that are clearly fake are fine.
- Flag workflow changes that give a job secrets, write permissions or deploy access it does not need. Workflows should declare `permissions` explicitly and pin third-party actions to a commit SHA.
- Flag changes that weaken a guardrail: skipping or loosening `tests/run`, narrowing the merge hook (`hooks/no-merge`) so a merge command is denied less or it fails open (`gh pr merge`, the merge API through `gh api` and auto-merge are denied, except the one command `gh pr merge <N> --merge --match-head-commit <sha>` that passes only with `MENTAT_AGENT_MERGE` on), a change to the hook that passes any merge form beyond that one, or instructions that let an agent deploy, publish or release, or merge beyond its own pull request with that setting on, including through auto-merge or `--admin`; narrowing the `mentat-public-text` module's hook or its GitHub MCP write matcher so a listed `gh` or MCP write with a hit is denied less; narrowing the git hooks (`git-hooks/`) so an update of a remote's default branch, the first branch pushed to a remote with none, or a staged or pushed likely secret passes (a push to a local path or `file://` URL may update any branch), or so they stop running the repository's own hooks.
- Flag shell scripts that break on paths with spaces or ignore a failing command.
- Flag text that states one user's preference rather than a rule or deliberate default every Mentat user needs. Leave such a preference to the user's own instructions.
- The merge hook, the `mentat-public-text` hook and the git hooks are nets for mistakes, not security boundaries: another command form that would merge or publish a hit without a denial, or push to the default branch or commit a likely secret without a refusal, is not a finding.
- Flag only problems with a realistic trigger. A check that fails closed is not a finding, and neither is input that needs a broken or hostile setup on the maintainer's own machine. Prefer removing code to adding guards.
