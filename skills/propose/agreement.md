# The plan check and the agreement question

Read this at `mentat:propose` step 4, and again after a compaction.

## The plan check

The plan check is one check, one round. Its idea file also holds the material assumptions and the failures that would become requirements known then (`mentat:propose` step 5), plus one line naming the failures considered and left out, the survey of established practice when one ran (`decisions.md` "Recommendations"), each objection of the maintainer's recorded on the item or on an item its work moved from (`../backlog/agent-records.md` "Decision lines"), with how the plan meets it or why it does not, and, for a change that gets a situation list (step 5), the full list. The spec carries the situations whose outcome the change decides as one numbered requirement, so the spec keeps the shape `mentat:backlog` "Agreement" gives, except that this one requirement runs one lettered line per situation instead of one or two lines.

A reply is a plan check only when its last line is exactly one of the three `PLAN CHECK VERDICT:` lines. A reply without one, an error or an empty result never counts as a pass: Claude Code calls the checker once more with the same file, with no model override when the first call had `MENTAT_PLAN_CHECK_MODEL`'s, and when that gives no verdict either, the agreement question says the plan check did not happen and why. Claude Code settles each point of the reply, adopting it or not, as `mentat:backlog` "Replies in chat" shows; an adopted change is not checked again, and a later recommendation that conflicts with an adopted point is handled as `decisions.md` says for a conflict with an earlier answer. A situation the reply names as missing from the list, or as having conflicting outcomes, is not left open: before the agreement question Claude Code decides its outcome, asking the maintainer only a decision that is theirs (`mentat:propose` step 3), and adds it to the list, or corrects its line. An adopted change that adds a mechanism (a new state, step, answer or owner) adds its own situations to the list before the agreement question, with no second check.

## The agreement question

The agreement question is asked in the message form `decisions.md` gives, with its four answers named. It names, each in a few words, only what the maintainer gets; what it costs, naming any hand check offered (which holds the pull request back from merge until they report it, or, as a step after the merge, does not, a failed one then needing a follow-up change, `mentat:propose` step 5) with roughly how much hand work it takes, and any fast track proposed (`mentat:propose` step 6); each material assumption still standing and what changes if it is false, this being where the maintainer sees them; the plan check's verdict when it is `DO IT DIFFERENTLY` or `DON'T`, with why; each tool of a second opinion the maintainer's own instructions add that disagreed (`DO IT DIFFERENTLY` or `DON'T`), with why; each open maintainer comment that bears on the agreement, with its answer, where an objection to the options revises them or the question says why they stand (`mentat:backlog` "Reading an item"); each recorded objection the idea file lists, in a few words, with how the plan, as it stands after any adopted plan-check changes, meets it or why it does not; and these facts: it names any such tool that gave no answer (it failed, timed out or is not installed, or outside reviewers are not on here: exit 6, not a failure or a block), says when the plan check gave no verdict, or was retried without `MENTAT_PLAN_CHECK_MODEL`, naming the model it asked for, and counts the changes adopted from it, which no check saw, naming as unchecked the situations those changes added to the list. It also says why the first answer is recommended, as `decisions.md` requires; the replies blocks and the full proposal stay out of it. Detail an item needs beyond its few words is given by "Show the full proposal".

Its first answer is the recommended one: "Not now" only while the session's own advice against building this plan stands (its view recommends closing or not building the item, or a smaller scope than the plan being agreed, and the maintainer has not answered that recommendation; or the plan check says `DON'T` and the session adopts it), else "Agree and build now" where the maintainer wants it built in this session, else "Agree, build later". The other three follow it in the order "Agree and build now", "Agree, build later", "Show the full proposal", "Not now", leaving out the one already first. "Show the full proposal" prints in chat the plan check's replies block, and any second opinion's, as `mentat:backlog` "Replies in chat" says, never a saved reply file, and the full proposal (`mentat:propose` step 5). When the maintainer objects to the item's design or plan in the talk after "Not now" (`mentat:propose` step 4), the session writes one decisions line on the item recording each objection (`../backlog/agent-records.md` "Decision lines").
