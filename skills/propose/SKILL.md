---
name: propose
description: "Use before a view on or suggesting a repo change; after compaction or resume mid-proposal. Typed, plans backlog work. Arguments: a backlog item id."
argument-hint: "[item id]"
---

When the maintainer's own message is the `/mentat:propose` command with no argument or one item id (one word shaped like an id, such as `ABC-12` or `#12`), read `session.md` in this skill's folder and follow it: one planning session, which runs once, then normal work resumes. With no id it covers the project's open Backlog and Todo items and the decisions open on them; with one, that item, and an id that is not this project's stops as its step 2 says. Typed with other text (such as `/mentat:propose fix the typo in X`), that text is the request, handled as a chat request by everything below. Who started the run decides: when Claude Code itself calls this skill through the Skill tool, with or without an item id (to start a change), it runs everything below, the small-request path and "Starting a build" included, and starts no planning session, except on the maintainer's yes to the order question of `mentat-linear:triage` "Report", which starts it with the offered items as its subject, in that order (`session.md`); a session already running goes on after a compaction, reading `session.md` again.

A change Claude Code suggests itself within the request it is carrying out, a fix to its own output included, counts as a request here. Any other change it suggests, or a defect it finds, is filed as `mentat:backlog` "Filing" routes it (a proposal to the Inbox, a defect to Backlog), not agreed here. The plan check's `DO IT` is not the maintainer's agreement, and nothing is built before that agreement, the one exception an item `mentat-lead:orchestrate` agrees by default (its "Planning"). The maintainer agrees once. Agreed work gets no further plan check. Scope that triage merged into committed work is not committed: it gets its plan check and agreement when that work is next planned. A batch needs agreement under one spec whose numbered requirements cover each change. Accepting an Inbox item in triage is not a commitment; the maintainer's yes here commits the item from Backlog to Todo.

A small, clear request (one line, nothing for the maintainer to decide, no material assumption, no failure step 5 would make a requirement and no situation list step 5 would require, no objection of the maintainer's recorded for the work (`../backlog/agent-records.md` "Decision lines"), such as fixing a typo) gets a one-line view, and the maintainer's answer to it is the agreement: no decisions or plan check, no grill beyond the offer step 2 makes before a new feature or workflow change is agreed, and no backlog read for a request with no item. A request about an existing backlog item first gets that item's full read (`mentat:backlog` "Reading an item"); an open maintainer comment on it takes the request off this path, and an incomplete read ends it as step 1 says. Its agreement offers only three of step 4's answers, "Agree and build now", "Agree, build later" and "Not now", with the same effects, and step 7 records the chosen answer with the fingerprint. When the change has something to try, the one-line view also offers the hand check of step 5. Step 1's freshness check, its skeptic's pass for an existing backlog item, and steps 6 and 7 still apply. A request that changes the meaning of what an agent is told in Mentat's `rules.md`, skills or builder prompt, or in a repository's `AGENTS.md` or other standing agent instructions, is not small and gets the plan check, however short. Every other request follows steps 1 to 7. A change to text every session loads (such as `rules.md` or the maintainer's own instructions) replaces or tightens existing text: its spec names the text it replaces or tightens, and adds new text only where no existing text covers the case.

1. Before reading code or asking the maintainer anything, Claude Code fetches origin's default branch and compares the checkout with it; if the fetch fails, it compares with the local copy and says so. When the checkout lacks commits there, Claude Code fast-forwards it if it is a clean checkout of that branch; otherwise it stops and says why. A checkout that lacks none goes on. Then Claude Code reads the request's existing backlog item, if any, in full as `mentat:backlog` "Reading an item" says; when that read stays incomplete, it says so, gives no view and runs none of steps 2 to 7 for that item. Otherwise it reads the code and the open backlog's titles and opening sentences (read only), runs the skeptic's pass below when the request picks up an existing item, then, for a new feature or workflow change, the survey `decisions.md` "Recommendations" gives, then a teammate's view (worth doing or not, the cost, a better way, overlapping items and the plan around them, with evidence). A view `session.md` step 4 already gave in this session for the same item and scope is not repeated; a changed scope gets a new one. The skeptic's pass runs on the session's own model (no subagent, Codex or Grok) over that item's records only (description, spec, every comment) and the code they name: every recorded assumption and decision still in force, the maintainer's (as summarized on the item) included, is questioned on the same terms against the code and the item's goal. It runs once per item per session unless the item's records, scope or that code changed. A finding needs evidence (code, a record or a checked fact) and shows how it affects a premise the work still relies on, or its outcome, scope, cost or risk; a later comment or changed file is a reason to look, not a finding. One the maintainer decides under `rules.md` goes to them as one decision question built as `rules.md` "What goes to the maintainer" says, asked as revisiting when it conflicts with a recorded answer; the session settles the rest and names each in one line. A doubt without evidence, or a point already answered with no new evidence since, is not raised.
2. Before agreeing a new feature or workflow change with two or more of the maintainer's decisions open, it first offers a grill (`mentat-lead:grill`) to ask them, unless a grill already ran for this request, and with one open asks it directly (step 3); a planning session makes this offer before the item's interview (`session.md` step 4). At any step before the work is agreed, once the maintainer has corrected the same point twice in the session, it offers a grill only if the corrections show one of their decisions is still open. Whichever fires, `session.md` step 4's offers included, it offers a grill only where that skill is available, at most once per request, and starts it only if the maintainer agrees.
3. Otherwise, or for any the grill leaves open, it asks only the decisions the maintainer can make now, each as `decisions.md` in this skill's folder says, never one already answered unless step 1's pass revisits it, and decides or defers the rest; one it does not need in order to go on goes as `decisions.md` says. When it records on an item an answer to a decision asked here or in a grill, as its decisions line (`mentat:backlog` "Item shape"), it also posts the answer reply for the open maintainer comments it answered (`mentat:backlog` "Reading an item").
4. Once the maintainer's open decisions are settled, it runs the plan check: one call of the `mentat:plan-checker` subagent, its model the value of `MENTAT_PLAN_CHECK_MODEL` (read by name with `printenv MENTAT_PLAN_CHECK_MODEL`, never the whole environment), or no model override when that is unset or empty, naming the commit the checkout is at and an idea file holding the idea, answers (with any grill's record, as `mentat-lead:grill` defines it) and deferred choices (not its own view), written in the project's ignored working folder, else a temporary folder, and kept until the item exists (`mentat:backlog` "Plan check record"); a second opinion the maintainer's own instructions add runs on the same idea file after the plan check is settled, its output saved to a file as it runs and kept until the item exists (`mentat:backlog` "Second opinion records"); it waits for every reply before the agreement question. Read `agreement.md` in this skill's folder at this step, and again after a compaction. It asks the maintainer to agree once, after the plan check, without showing its reply first, unless `mentat-lead:orchestrate` agrees by default. "Agree and build now" commits the item to Todo and starts its build, checks and reviews; "Agree, build later" commits it to Todo and starts nothing; "Show the full proposal" records nothing and runs no further check, then asks the same agreement question again; "Not now" is an answer named as committing nothing and opening a talk: it goes on in chat, and when the maintainer says there, or in their reply, to leave the item, that is their answer: the agreement ends as it stands and is not asked again until the item is next planned. When the maintainer objects in that talk to the item's design or plan, the session writes one decisions line on the item recording each objection (`../backlog/agent-records.md` "Decision lines"). Only an Agree answer, or the one exception, `mentat-lead:orchestrate`'s default agreement, writes the spec, records the fingerprint or moves the item. In a chat request, "Agree and build now", unless `../build/redirect.md` applies, goes on to build in this session as `rules.md` says, from the builder, its model as `../build/helpers.md` "Briefs" says, to `mentat:review`, each builder's brief carrying the item's recorded assumptions as given, when any stand, read through `mentat:backlog` "Material assumptions" right before the brief, and "Agree, build later" stops once step 7 is done. "Agree and build now" applies `mentat:backlog` "Start waits" before any branch or build session, unless redirected: an item held by its start wait is committed but not started in that turn, and the reply names its wait. An item committed for later is built only when the maintainer types `/mentat:build`, with or without its id, or says yes to a next-work offer naming it.
5. The proposal says in the maintainer's terms what changes for them, what it adds to or drops from the request, and how the result will be checked; build detail goes in the spec, not chat. It names the material assumptions: unchecked facts the plan relies on that would change the design or the checks if false, each with what changes if false. A fact that can be checked is checked instead; with none left, the part is left out, never written as "none". Every change that alters behavior, instruction text included, gets a failure check while planned: a failure tightens a numbered requirement, or becomes a new one, only with a realistic trigger and when the named checks would miss it or it changes what the maintainer gets, pays or risks; a rare or harmless case, or a misreading the review criteria's wording rule already covers, stays out. There is no standing failure section. A change to how work passes between sessions or agents (handovers, relays, waits, takeovers, after-merge steps), or to a hand-written parser, also gets a situation list while planned: each event or state it must handle and what happens in it, one line each, listing only situations whose outcomes differ; no other change gets one. A parser's list names classes of input and decides each class as a whole, accepted or refused, rather than sibling cases one by one. When the change has something the maintainer can try in a few minutes (a screen, a page, a command's output, a behavior they can trigger), the proposal offers them a hand check, saying what they would try, roughly how much hand work it takes, and that a hand check they accept holds the pull request back from merge until they report it, or, for a change that takes effect only once merged, that it is a step after the merge, which does not hold it back, and a failed check then needs a follow-up change. A check whose failing result would change nothing gets no offer.
6. Claude Code may propose a fast track (no review runs; tests, CI and the final check still do) for a change that cannot alter what code does or what an agent is told; the spec records it with its reason.
7. Once agreed, with either answer, it writes the spec (shape in `mentat:pr`) where `mentat:backlog` "Where the spec lives" says, creating the item first when the request has none (with GitHub issues, an issue), so the spec, the fingerprint record and the Todo stage are recorded on it, and, unless the backlog is external, in the pull request once open. Committing to Todo always needs an item. It also writes a decisions line for each decision of the maintainer's settled while planning, a grill's or step 3's, that the item does not hold yet (`mentat:backlog` "Item shape"). When the agreed item must wait on other items, the same write adds its start wait, read back before the Todo move (`mentat:backlog` "Start waits"). On the item it then records the spec's fingerprint and the chosen answer (build now or later, or agreed by default), as `mentat:backlog` "Agreement" says, and again whenever an agreed change of scope rewrites the spec. At agreement it also records the material assumptions still standing as `mentat:backlog` "Material assumptions" says. Recording the answer also posts the answer reply for the open maintainer comments it answered (`mentat:backlog` "Reading an item"). When Claude Code had recommended closing, shrinking or not building the item and the maintainer agreed anyway, it also records the advice as `mentat:backlog` "Advice against" says. The spec lists a requirement the maintainer checks by hand only when their agreement accepts the offer or they asked for one. When the change adds a skill that takes arguments (text typed after its command) or changes what they do, the spec says what a run with no arguments does. A skill that takes project names, run with none, asks once which projects to cover before it reads or writes anything else: the session's project first, then `all`, another through Other. Where the maintainer's own instructions name no project list, it asks nothing and covers the session's repository.

## Starting a build
A build `session.md` step 8 or a yes to a next-work offer (`../backlog/next-work.md`) starts runs in this session: Claude Code calls the Skill tool with `mentat:build` and the ids, in that order. A build runs in its own session only when the maintainer asks for that, or when this session says, before it starts, why the queue is too long to carry here; it then gives one fenced line, the full `/mentat:build <ids>` command, for the maintainer to run in a new session in its own fresh checkout (worktree). A session running `mentat-lead:orchestrate` never builds in itself, a chat request's build included: it starts or hands over to its build session as that skill says.
