name: propose
description: "Starts a change (step 1). Use before giving a view on any request that may change a repository or before suggesting such a change of its own, and after a compaction or a resumed session while this step is in progress."
user-invocable: false
---

A change Claude Code suggests itself within the request it is carrying out, a fix to its own output included, counts as a request here. Any other change it suggests, or a defect it finds, is filed as `rules.md` "What goes to the maintainer" routes it (a proposal to the Inbox, a defect to Backlog), not agreed here. A second opinion's `DO IT` is not the maintainer's agreement, and nothing is built before that agreement. The maintainer agrees once. Agreed work gets no further second opinion. Scope that triage merged into committed work is not committed: it gets its second opinion and agreement when that work is next planned. A batch needs agreement under one spec whose numbered requirements cover each change. Accepting an Inbox item in triage is not a commitment; the maintainer's yes here commits the item from Backlog to Todo.

A small, clear request (one line, nothing for the maintainer to decide, such as fixing a typo) gets a one-line view, and the maintainer's answer to it is the agreement: no grill, decisions or `mentat second-opinion`, and no backlog read for a request with no item. A request about an existing backlog item first gets that item's full read (`mentat:backlog` "Reading an item"); an incomplete read or an open maintainer comment on it takes the request off this path. Its agreement offers only three of step 4's answers, "Agree and build now", "Agree, build later" and "Not now", with the same effects, and step 7 records the chosen answer with the fingerprint. When the change has something to try, the one-line view also offers the hand check of step 5. Step 1's freshness check and steps 6 and 7 still apply. A request that changes the meaning of what an agent is told in Mentat's `rules.md`, skills or builder prompt, or in a repository's `AGENTS.md` or other standing agent instructions, is not small and gets the second opinion (`mentat second-opinion`), however short. Every other request follows steps 1 to 7. A change to text every session loads (such as `rules.md` or the maintainer's own instructions) replaces or tightens existing text before it adds any: its spec names the text it replaces or tightens, and adds new text only where no existing text covers the case.

1. Before reading code or asking the maintainer anything, Claude Code fetches origin's default branch and compares the checkout with it; if the fetch fails, it compares with the local copy and says so. When the checkout lacks commits there, Claude Code fast-forwards it if it is a clean checkout of that branch; otherwise it stops and says why. A checkout that lacks none goes on. Then Claude Code reads the request's existing backlog item, if any, in full as `mentat:backlog` "Reading an item" says, then the code and the open backlog's titles and opening sentences (read only), then gives a teammate's view (worth doing or not, the cost, a better way, overlapping items and the plan around them, with evidence). A view `mentat:plan` step 4 already gave in this session for the same item and scope is not repeated; a changed scope gets a new one.
2. For a new feature or workflow change, when several open decisions depend on each other, it may first offer a grill (`mentat:grill`) to ask them. At any step before the work is agreed, once the maintainer has corrected the same point twice in the session, it offers a grill only if the corrections show one of their decisions is still open. Whichever fires, it offers a grill at most once per request, and starts it only if the maintainer agrees.
3. Otherwise, or for any the grill leaves open, it asks only the decisions the maintainer can make now, never one already answered, and decides or defers the rest; one it does not need in order to go on goes as `rules.md` "What goes to the maintainer" says. Whenever it records an answer on an item, here or in step 7, it posts the answer reply for the open maintainer comments it answered (`mentat:backlog` "Reading an item").
4. Once the maintainer's open decisions (theirs, not technical ones) are settled, it runs the second opinion (`mentat second-opinion`) on a file with the idea, answers (with any grill's record, as `mentat:grill` defines it) and deferred choices (not its own view), saving the command's output to a file as it runs, in the project's ignored working folder, else a temporary folder, and keeping it until the item exists (`mentat:backlog` "Second opinion records"). It runs another round only when the last round's settlement adopts a change to the idea's requirements, scope or approach; a wording-only change does not count. The rounds stop when a settlement adopts no such change, or after three rounds in all. Each later round's file holds the whole revised idea, with its answers and deferred choices, and no earlier replies or summary of them. A round in which no tool gives a verdict stops the rounds. It asks the maintainer to agree once, after the last round, only after every reply is in, without showing the replies first. That question holds only what the maintainer gets; what it costs, naming any hand check offered (which holds back "Ready to merge: #N" until they report it, step 5) and any fast track proposed (step 6); each tool that disagreed (`DO IT DIFFERENTLY` or `DON'T`), with why in a few words; and these facts: it names any tool that gave no answer (it failed, timed out or is not installed), says when the last adopted change had no second opinion, and says when a round did not happen because no tool gave a verdict. It also says why the first option is recommended, as `rules.md` "What goes to the maintainer" requires; the replies blocks and the full proposal stay out of it. Its first two options are "Agree and build now", which commits the item to Todo and starts its build, checks and reviews, and "Agree, build later", which commits it to Todo and starts nothing; the first is recommended where the maintainer wants it built in this session. Its third, "Show the full proposal", prints in chat every round's replies block as `mentat:backlog` "Replies in chat" says, never the saved command output, and the full proposal (step 5); it records nothing, commits nothing and runs no round, then asks the same agreement question again. Its last option, "Not now", commits nothing and records no fingerprint. Only an Agree answer writes the spec, records the fingerprint or moves the item. In a chat request, "Agree and build now" goes on to build in this session through `rules.md` "A change" steps 2 to 5, and "Agree, build later" stops once step 7 is done. "Agree and build now" applies `mentat:backlog` "Start waits" before any branch or build session: an item held by its start wait is committed but not started in that turn, and the reply names its wait. An item committed for later is built only when the maintainer types `/mentat:build`, with or without its id, or says yes to a next-work offer naming it.
5. The proposal says in the maintainer's terms what changes for them, what it adds to or drops from the request, and how the result will be checked; build detail goes in the spec, not chat. When the change has something the maintainer can try in a few minutes (a screen, a page, a command's output, a behavior they can trigger), the proposal offers them a hand check. It says what they would try, and that a hand check they accept holds back "Ready to merge: #N" until they report it. A change with nothing to try gets no offer.
6. Claude Code may propose a fast track (no Codex or Grok review) for a change that cannot alter what code does or what an agent is told; the spec records it with its reason.
7. Once agreed, with either answer, it writes the spec (shape in `mentat:pr`) in the backlog item, creating the item first when the request has none (with GitHub issues, an issue), so the spec, the fingerprint comment and the Todo stage are recorded on it, and, unless the backlog is external, in the pull request once open. Committing to Todo always needs an item. When the agreed item must wait on another item, a pull request or a count, the same write adds its start wait line (`mentat:backlog` "Start waits"). On the item it then records the spec's fingerprint and the chosen answer (build now or later), as `mentat:backlog` "Agreement" says, and again whenever an agreed change of scope rewrites the spec. When Claude Code had recommended closing, shrinking or not building the item and the maintainer agreed anyway, it also posts the advice comment `mentat:backlog` "Advice against" gives. For each item the agreement commits, when a second opinion round ran, it runs `mentat second-opinion --link <item id> <idea file>` with the last round's idea file; the link calls no model and is not another second opinion. When it links nothing, the agreement stands and step 7 goes on. The spec lists a requirement the maintainer checks by hand only when their agreement accepts the offer or they asked for one. When the change adds a skill that takes arguments (text typed after its command) or changes what they do, the spec says what a run with no arguments does. A skill that takes project names, run with none, asks once which projects to cover before it reads or writes anything else: the session's project first, then `all`, another through Other. Where the maintainer's own instructions name no project list, it asks nothing and covers the session's repository.

## Starting a build
A session that starts a build session (`mentat:plan` step 8, or a forwarded yes as `../backlog/next-work.md` says) writes the build command into the brief as its own word after plain text: a slash, the command name and the ids, with no backtick, quote or other mark touching it. Every other command name in the brief stays in backticks. The brief tells the started session to call the Skill tool with that command and those ids, and that if the Skill tool refuses the call, it stops with nothing changed, does not follow the skill's steps by hand, and sends the typed command `/mentat:build <ids>` to the starting session.

When the host refuses to start a build session in this turn but can propose one that the maintainer starts in one step, the session instead proposes each build session its caller would start, in the caller's order and with the same brief, and ends the turn saying one step starts them, with no next-work question in that turn. A proposal counts only when starting it opens a new session in its own fresh checkout (worktree); one that would run in this session or in this checkout does not. The maintainer's start of a proposal, or their next message telling this session to start them, starts each build session not yet started, once; before starting on a message, the session checks the host's session state, so a build already started is never started again. Only where the host can do neither, it gives each build session, in the caller's order, its own fenced line the maintainer can paste to start its build: the full `/mentat:build <ids>` command; with more than one line, it says each build run gets its own fresh checkout (worktree). Running it asks no further yes. A forwarded yes starts its one build session; `mentat:plan` step 8 starts one per group. The Skill tool refusal above stays separate: it applies inside a started session.
