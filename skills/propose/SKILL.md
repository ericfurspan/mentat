A change Claude Code suggests itself within the request it is carrying out, a fix to its own output included, counts as a request here. Any other change it suggests, or a defect it finds, is filed as `rules.md` "What goes to the maintainer" routes it (a proposal to the Inbox, a defect to Backlog), not agreed here. The plan check's `DO IT` is not the maintainer's agreement, and nothing is built before that agreement. The maintainer agrees once. Agreed work gets no further plan check. Scope that triage merged into committed work is not committed: it gets its plan check and agreement when that work is next planned. A batch needs agreement under one spec whose numbered requirements cover each change. Accepting an Inbox item in triage is not a commitment; the maintainer's yes here commits the item from Backlog to Todo.

A small, clear request (one line, nothing for the maintainer to decide, no material assumption and no failure step 5 would make a requirement, such as fixing a typo) gets a one-line view, and the maintainer's answer to it is the agreement: no grill, decisions or plan check, and no backlog read for a request with no item. A request about an existing backlog item first gets that item's full read (`mentat:backlog` "Reading an item"); an open maintainer comment on it takes the request off this path, and an incomplete read ends it as step 1 says. Its agreement offers only three of step 4's answers, "Agree and build now", "Agree, build later" and "Not now", with the same effects, and step 7 records the chosen answer with the fingerprint. When the change has something to try, the one-line view also offers the hand check of step 5. Step 1's freshness check, its skeptic's pass for an existing backlog item, and steps 6 and 7 still apply. A request that changes the meaning of what an agent is told in Mentat's `rules.md`, skills or builder prompt, or in a repository's `AGENTS.md` or other standing agent instructions, is not small and gets the plan check, however short. Every other request follows steps 1 to 7. A change to text every session loads (such as `rules.md` or the maintainer's own instructions) replaces or tightens existing text before it adds any: its spec names the text it replaces or tightens, and adds new text only where no existing text covers the case.

1. Before reading code or asking the maintainer anything, Claude Code fetches origin's default branch and compares the checkout with it; if the fetch fails, it compares with the local copy and says so. When the checkout lacks commits there, Claude Code fast-forwards it if it is a clean checkout of that branch; otherwise it stops and says why. A checkout that lacks none goes on. Then Claude Code reads the request's existing backlog item, if any, in full as `mentat:backlog` "Reading an item" says; when that read stays incomplete, it says so, gives no view and runs none of steps 2 to 7 for that item. Otherwise it reads the code and the open backlog's titles and opening sentences (read only), runs the skeptic's pass below when the request picks up an existing item, then gives a teammate's view (worth doing or not, the cost, a better way, overlapping items and the plan around them, with evidence). A view `mentat:plan` step 4 already gave in this session for the same item and scope is not repeated; a changed scope gets a new one. The skeptic's pass runs on the session's own model (no subagent, Codex or Grok) over that item's records only (description, spec, every comment) and the code they name: every recorded assumption and decision still in force, the maintainer's (as summarized on the item) included, is questioned on the same terms against the code and the item's goal. It runs once per item per session unless the item's records, scope or that code changed. A finding needs evidence (code, a record or a checked fact) and shows how it affects a premise the work still relies on, or its outcome, scope, cost or risk; a later comment or changed file is a reason to look, not a finding. One the maintainer decides under `rules.md` goes to them as one decision question built as `rules.md` "What goes to the maintainer" says, asked as revisiting when it conflicts with a recorded answer; the session settles the rest and names each in one line. A doubt without evidence, or a point already answered with no new evidence since, is not raised.
2. For a new feature or workflow change, when several open decisions depend on each other, it may first offer a grill (`mentat:grill`) to ask them. At any step before the work is agreed, once the maintainer has corrected the same point twice in the session, it offers a grill only if the corrections show one of their decisions is still open. Whichever fires, it offers a grill at most once per request, and starts it only if the maintainer agrees.
3. Otherwise, or for any the grill leaves open, it asks only the decisions the maintainer can make now, never one already answered unless step 1's pass revisits it, and decides or defers the rest; one it does not need in order to go on goes as `rules.md` "What goes to the maintainer" says. When it records an answer on an item here, it posts the answer reply for the open maintainer comments it answered (`mentat:backlog` "Reading an item").
4. Once the maintainer's open decisions (theirs, not technical ones) are settled, it runs the plan check: one call of the `mentat:plan-checker` subagent, with no model override, naming the commit the checkout is at and an idea file holding the idea, answers (with any grill's record, as `mentat:grill` defines it) and deferred choices (not its own view), written in the project's ignored working folder, else a temporary folder, and kept until the item exists (`mentat:backlog` "Plan check record"); it waits for the reply before the agreement question. Read `agreement.md` in this skill's folder at this step, and again after a compaction: it says what else the idea file holds, how the reply is settled and what the agreement question holds. It asks the maintainer to agree once, after the plan check, without showing its reply first. "Agree and build now" commits the item to Todo and starts its build, checks and reviews; "Agree, build later" commits it to Todo and starts nothing; "Show the full proposal" records nothing, commits nothing and runs no further check, then asks the same agreement question again; "Not now" commits nothing and records no fingerprint. Only an Agree answer writes the spec, records the fingerprint or moves the item. In a chat request, "Agree and build now" goes on to build in this session through `rules.md` "A change" steps 2 to 5, each builder's brief carrying the item's latest assumptions comment as given, when one exists, read through `mentat:backlog` "Material assumptions" right before the brief, and "Agree, build later" stops once step 7 is done. "Agree and build now" applies `mentat:backlog` "Start waits" before any branch or build session: an item held by its start wait is committed but not started in that turn, and the reply names its wait. An item committed for later is built only when the maintainer types `/mentat:build`, with or without its id, or says yes to a next-work offer naming it.
5. The proposal says in the maintainer's terms what changes for them, what it adds to or drops from the request, and how the result will be checked; build detail goes in the spec, not chat. It names the material assumptions: unchecked facts the plan relies on that would change the design or the checks if false, each with what changes if false. A fact that can be checked is checked instead; with none left, the part is left out, never written as "none". Every change that alters behavior, instruction text included, gets a failure check while planned: a failure tightens a numbered requirement, or becomes a new one, only with a realistic trigger and when the named checks would miss it or it changes what the maintainer gets, pays or risks; a rare or harmless case, or a misreading the review criteria's wording rule already covers, stays out. There is no standing failure section. When the change has something the maintainer can try in a few minutes (a screen, a page, a command's output, a behavior they can trigger), the proposal offers them a hand check. It says what they would try, and that a hand check they accept holds back "Ready to merge: #N" until they report it. A change with nothing to try gets no offer.
6. Claude Code may propose a fast track (no Codex or Grok review) for a change that cannot alter what code does or what an agent is told; the spec records it with its reason.
7. Once agreed, with either answer, it writes the spec (shape in `mentat:pr`) in the backlog item, creating the item first when the request has none (with GitHub issues, an issue), so the spec, the fingerprint comment and the Todo stage are recorded on it, and, unless the backlog is external, in the pull request once open. Committing to Todo always needs an item. When the agreed item must wait on another item, a pull request or a count, the same write adds its start wait line (`mentat:backlog` "Start waits"). On the item it then records the spec's fingerprint and the chosen answer (build now or later), as `mentat:backlog` "Agreement" says, and again whenever an agreed change of scope rewrites the spec. At agreement it also posts the material assumptions still standing as `mentat:backlog` "Material assumptions" says. Recording the answer also posts the answer reply for the open maintainer comments it answered (`mentat:backlog` "Reading an item"). When Claude Code had recommended closing, shrinking or not building the item and the maintainer agreed anyway, it also posts the advice comment `mentat:backlog` "Advice against" gives. For each item the agreement commits, when a second opinion round ran, it runs `mentat second-opinion --link <item id> <idea file>` with the last round's idea file; the link calls no model and is not another second opinion. When it links nothing, the agreement stands and step 7 goes on. The spec lists a requirement the maintainer checks by hand only when their agreement accepts the offer or they asked for one. When the change adds a skill that takes arguments (text typed after its command) or changes what they do, the spec says what a run with no arguments does. A skill that takes project names, run with none, asks once which projects to cover before it reads or writes anything else: the session's project first, then `all`, another through Other. Where the maintainer's own instructions name no project list, it asks nothing and covers the session's repository.

## Starting a build
A build `mentat:plan` step 8 or a yes to a next-work offer (`../backlog/next-work.md`) starts runs in this session: Claude Code calls the Skill tool with `mentat:build` and the ids, in that order. A build runs in its own session only when the maintainer asks for that, or when this session says, before it starts, why the queue is too long to carry here; it then gives one fenced line, the full `/mentat:build <ids>` command, for the maintainer to run in a new session in its own fresh checkout (worktree).
