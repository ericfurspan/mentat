---
name: propose
description: "Starts a change (step 1). Use before giving a view on any request that may change a repository or before suggesting such a change of its own, and after a compaction or a resumed session while this step is in progress."
user-invocable: false
---

A change Claude Code suggests itself within the request it is carrying out, a fix to its own output included, counts as a request here. Any other change it suggests, or a defect it finds, is filed as `rules.md` "What goes to the maintainer" routes it (a proposal to the Inbox, a defect to Backlog), not agreed here. A design review's `DO IT` is not the maintainer's agreement, and nothing is built before that agreement. The maintainer agrees once. Agreed work gets no second design review. Scope that triage merged into committed work is not committed: it gets its design review and agreement when that work is next planned. A batch needs agreement under one spec whose numbered requirements cover each change. Accepting an Inbox item in triage is not a commitment; the maintainer's yes here commits the item from Backlog to Todo.

A small, clear request (one line, nothing for the maintainer to decide, such as fixing a typo) gets a one-line view, and the maintainer's yes to it is the agreement: no backlog read, grill, decisions, `mentat weigh` or `mentat:challenge`. That yes is agreement to build now: it commits the item to Todo and starts its build, checks and reviews. When the change has something to try, the one-line view also offers the hand check of step 5. Step 1's freshness check and steps 6 and 7 still apply. A request that changes the meaning of what an agent is told in Mentat's `rules.md`, skills or builder prompt, or in a repository's `AGENTS.md` or other standing agent instructions, is not small and gets the design review (`mentat weigh`), however short. Every other request follows steps 1 to 8.

1. Before reading code or asking the maintainer anything, Claude Code fetches origin's default branch and compares the checkout with it; if the fetch fails, it compares with the local copy and says so. When the checkout lacks commits there, Claude Code fast-forwards it if it is a clean checkout of that branch; otherwise it stops and says why. A checkout that lacks none goes on. Then Claude Code reads the code and the open backlog's titles and opening sentences (read only), then gives a teammate's view (worth doing or not, the cost, a better way, overlapping items and the plan around them, with evidence).
2. For a new feature or workflow change, when several open decisions depend on each other, it may first offer a grill (`mentat:grill`) to ask them, at most once per request, and starts it only if the maintainer agrees.
3. Otherwise, or for any the grill leaves open, it asks only the decisions the maintainer can make now, never one already answered, and decides or defers the rest; one it does not need in order to go on goes as `rules.md` "What goes to the maintainer" says.
4. Once the maintainer's open decisions (theirs, not technical ones) are settled, it runs the design review (`mentat weigh`) on a file with the idea, answers (with any grill's record, as `mentat:grill` defines it) and deferred choices (not its own view). It runs another round only when the last round's settlement adopts a change to the idea's requirements, scope or approach; a wording-only change does not count. The rounds stop when a settlement adopts no such change, or after three rounds in all. Each later round's file holds the whole revised idea, with its answers and deferred choices, and no earlier replies or summary of them. A round in which no tool gives a verdict stops the rounds. It asks the maintainer to agree once, after the last round, only after every reply is in and shown as `mentat:backlog` "Replies in chat" says; that question names any tool that gave no answer (it failed, timed out or is not installed), says when the last adopted change had no design review, and says when a round did not happen because no tool gave a verdict. Its first two options are "Agree and build now", which commits the item to Todo and starts its build, checks and reviews, and "Agree, build later", which commits it to Todo and starts nothing; the first is recommended where the maintainer wants it built in this session, and the question's other options stay. In a chat request, "Agree and build now" goes on to build in this session through `rules.md` "A change" steps 2 to 5, and "Agree, build later" stops once step 7 is done. An item committed for later is built only when the maintainer types `/mentat:work-tickets`, with or without its id, or says yes to a next-work offer naming it.
5. The proposal says in the maintainer's terms what changes for them, what it adds to or drops from the request, and how the result will be checked; build detail goes in the spec, not chat. When the change has something the maintainer can try in a few minutes (a screen, a page, a command's output, a behavior they can trigger), the proposal offers them a hand check. It says what they would try, and that a hand check they accept holds back "You: merge #N." until they report it. A change with nothing to try gets no offer.
6. Claude Code may propose a fast track (no Codex or Grok review) for a change that cannot alter what code does or what an agent is told; the spec records it with its reason.
7. Once agreed, it writes the spec (shape in `mentat:pr`) in the backlog item (chat if none) and, unless the backlog is external, the pull request once open. On the item it then records the spec's fingerprint and the chosen answer (build now or later), as `mentat:backlog` step 6 says, and again whenever an agreed change of scope rewrites the spec. The spec lists a requirement the maintainer checks by hand only when their agreement accepts the offer or they asked for one. When the change adds a skill that takes arguments (text typed after its command) or changes what they do, the spec says what a run with no arguments does. A skill that takes project names, run with none, asks once which projects to cover before it reads or writes anything else: the session's project first, then `all`, another through Other. Where the maintainer's own instructions name no project list, it asks nothing and covers the session's repository.
8. If the approach is uncertain, the decision matters or the maintainer asks for a challenge, it calls the Skill tool with `mentat:challenge`.
