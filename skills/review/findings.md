# Findings

Read this when sorting review findings, and again after a compaction.

Claude Code sorts every review finding. It fixes what affects correctness, the stated requirements or security when the problem has a realistic trigger, and answers the rest with a reason, including edge cases that fail closed or need a broken local setup. On instruction text, a finding that only covers a rare or harmless case is answered with a reason, not fixed. A defect Claude Code finds or agrees is real is fixed in the pull request, at any round before the last within the limit, except at a pending stop (`stop.md`), where fixes wait until it is settled or answered; it goes to the maintainer only when the fix would change the agreed scope or, at the round limit, the head cannot be Ready, never into a follow-up item on its own, except one left at the round limit on a head that may be Ready; at the round limit, both come only after the extra round where `stop.md` "Round limit" allows one. A suggestion to handle leftovers of something the change removes, such as a rule for old data, a note that it is gone or a test that it stays gone, is not adopted; leftovers get a one-time cleanup instead, and the old form keeps support only where records the change cannot rewrite or a requirement still in force need it. Non-defect improvements become cheap fixes or follow-ups. A reviewer's blocking or non-blocking mark is a claim, and Claude Code's sorting decides each finding; of the findings it disagrees with, only those marked blocking and not settled by the maintainer go to the maintainer. A finding that only points at an error in the spec that a spec fix would have settled and that "Calls made without the maintainer" names is answered by that line, even when marked blocking: it is not fixed, not sent to the maintainer and not a blocker Claude Code disagrees with, and its Review details line gives that line as its reason, with no Risks line (`../backlog/spec-fixes.md`).

A finding raised again with no new evidence after its answer was recorded in Review details, unless it was settled by the maintainer and the text it was about changed since, by itself makes no stop pending (`stop.md`); it is answered by pointing to that line when it also names no specific error in that answer, and sorted on whether the error holds when it names one. One settled by the maintainer (`stop.md` "Round limit"), raised again with no new evidence and the text it was about unchanged, counts as answered: it does not keep the head from Ready, does not go to the maintainer again, and keeps its Risks line as a blocking finding answered instead of fixed. Raised again with new evidence, or a settled one after the text it was about changed, it is sorted like any finding; a settled one back with new evidence, the text it was about unchanged, still blocking and disputed, goes into the next limit question, which names the new evidence.

A fix to instruction text (skills, agent prompts, reviewer criteria, hook messages, and text every session loads, such as `rules.md` or the maintainer's own instructions) replaces or tightens existing text before it adds any: the fix names the text it replaces or tightens, and adds new text only where no existing text covers the case. A finding caused by the previous round's fix reworks that fix first, adding text only where a rework cannot cover it.
