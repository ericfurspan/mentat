name: linear
description: "Moves this repository's planning from GitHub issues to Linear, open issues included. Arguments: project and team names; with none, asks for them."
argument-hint: "[project name] [team name]"
disable-model-invocation: true
---

The maintainer wants this repository's planning moved from GitHub issues to a Linear project. The setting lives as prose in the repository's AGENTS.md. This runs once: do it, then normal work resumes. If the maintainer typed a project or team name after the command, start from that.

1. Read every AGENTS.md that applies (root and nested, and `AGENTS.override.md` if present, which replaces the AGENTS.md beside it) and show the backlog it names (the named external one, else GitHub issues). Change nothing yet. Ask for the project name and team the maintainer did not type, one decision at a time with a recommendation, as `rules.md` "What goes to the maintainer" says. Recommend the repository's name as the project name. The line written to AGENTS.md replaces the existing backlog sentence, never sits beside it: ``The external backlog is the Linear project `<name>`, in team `<team>`.``
2. Write the line in one pull request, by the normal path. The maintainer's answers above are the agreement, so the change gets no second opinion. The main session edits no files.
   - Put the spec (shape in `mentat:pr`) in the switch item (step 3). Requirements are numbered: the line in AGENTS.md, the migration and the closes. "Out of scope:" is last.
   - Run `mentat check`. Brief the `builder` subagent: the line, the AGENTS.md file to edit (the root one; the override if present), the file's own style, that the line replaces the existing backlog sentence, and to leave the rest alone. Run the repository's test command before the push when `rules.md` step 3 calls for it, call the Skill tool with `mentat:pr` for the body and with `mentat:review` for the loop.
   - The pull request reads its spec from the switch item, and every review is `mentat review --request <file> <N>` (and `--grok`), since AGENTS.md names the backlog only once the pull request merges. The pull request body writes no `Closes #`.
3. Linear. Before any Linear action, read `../backlog/linear.md` from this skill's folder (`mentat:backlog`'s "Tracker: Linear"), and again after a compaction. Load the Linear connector tools with ToolSearch (query `linear`). If they are missing, Linear is not connected: say so and stop; nothing has been created. Then, in order:
   - Find the team by name. If it is not there, stop and say so.
   - If a project of the chosen name exists in the team, stop and show it to the maintainer.
   - Create each of the team's labels in `../backlog/linear.md` that the team does not have yet.
   - If the Linear tools cannot write a project's short summary on its own or add a link under its Resources, stop and say so; create no project in another shape. Else ask the maintainer for the project's purpose line, one line saying what it is for, offering a draft from the README. Create the project in the new project shape in `../backlog/linear.md`, with that line as its short summary, the repository's link under Resources and the maintainer as lead. Then, before writing any item to it, tell the maintainer that Linear's GitHub integration can post an item's description, a wait block included, to GitHub, so they should set its "Comments in GitHub" to post without issue descriptions and turn it off for public repositories; agents do not change it.
   - Create the switch item first: title `Move planning from GitHub issues to this backlog`, label Improvement, status Todo, an opening sentence that says the maintainer asked for it in chat (`mentat:backlog`'s item shape), and a `## Spec` holding the AGENTS.md line, the migration and the closes, in public-safe words that name neither the workspace nor an item. Say the closes happen after the pull request merges, so the pre-merge review reads them as a post-merge step, not something the diff must contain. Set it In Progress when the branch exists.
   - Migrate the open issues (step 4). When the pull request is open, add the `Waiting on you` label and the lead's assignment (Linear step 4 in `../backlog/linear.md`) and the wait block to the switch item. A later session never loads this skill, so the block is self-contained: the heading "## Waits on the maintainer"; the pull request number; the issue numbers to close (the migrated issues and the pinned issue, not the held-back ones); the exact `gh issue close` command with the fixed comment, as in step 5; and the steps: merge the pull request, then, only once `gh pr view <N> --json state` reports merged, run the command for each listed issue, set the switch item to Done, remove the block and the label, and clear the assignee if it is still the project's lead; then the last line, `Ends when: the pull request is merged and each listed issue is closed`. This block stays even though it opens with a merge: its later steps are setup steps a later session must run, so `mentat:backlog` step 4's merge exception does not remove it.
4. Migration. One open GitHub issue at a time, from the main session (the builder never touches the backlog). The pinned issue is not migrated as an item: only its order is carried to the project, by creation order, and it is closed in step 5 with the others. Take the issues listed in the pinned issue's order first, in that order, then the rest by issue number, and set no Priority on any item. The agreed items are then created after the switch item in the pinned issue's order, else by issue number, and `mentat:backlog` step 5 ranks them oldest first.
   1. List the open issues. For each open issue, ask GitHub which pull requests close it (the owner and repository from `gh repo view --json nameWithOwner`):
      ```
      gh api graphql -f query='{ repository(owner:"<owner>", name:"<repo>") { issue(number:<N>) { closedByPullRequestsReferences(first:50, includeClosedPrs:true) { nodes { number state } } } } }'
      ```
      The query is per issue and complete: it returns every pull request GitHub links as closing the issue (GitHub's own reading of close, fix and resolve keywords), with `state` OPEN, MERGED or CLOSED. An issue with any OPEN node is still closed by an open pull request: it is not migrated and is held back. List those to the maintainer in one message, recommending they stay on GitHub until that pull request merges. Do not close them.
   2. Read the issue: `gh issue view <N> --json title,body,labels,state`.
   3. The spec is the issue's `## Spec` section, else its `## Agreed request`, heading kept, copied without rewording (pass the text through, never retype it). The item follows the item shape in `mentat:backlog`: an opening sentence in Claude Code's words; the issue's `## Waits on the maintainer` section first when it has one, with the `Waiting on you` label and the lead's assignment (Linear step 4 in `../backlog/linear.md`); the spec; `## Current plan` when the issue has one. Anything else in the body goes in the item's first comment, unchanged, labeled as copied from GitHub issue #N. The issue's own comments stay on the issue.
   4. Type from the label: `bug` is Bug, `enhancement` is Feature, else Improvement.
   5. Status. With stage labels: `idea` is the Inbox (below), no stage label is a Backlog item, `ready` is Todo, `in progress` is In Progress, `waiting` is the status of a waiting issue (below), plus the `Waiting on you` label and the lead's assignment (Linear step 4 in `../backlog/linear.md`). Without them, find the branches (`git ls-remote --heads origin`) and use the pull requests step 4.1's query returned. A branch belongs to the issue only when: the issue number is its own segment of a branch's name, set off by `/`, `-`, `_` or an end (`feat/10-globe`, `issue-10`, `10-globe`), not part of a longer number or a date, or the issue body names the branch. A pull request belongs to the issue only through that query. Any other resemblance does not count; when a branch might belong but does not meet this rule, the issue is held back like step 4.1's and listed to the maintainer with the ambiguous cases, not marked In Progress. Then:
      - An issue with a `## Waits on the maintainer` section is agreed work. It is In Progress when an open branch or open pull request belongs to it, or every pull request in the query is MERGED or CLOSED and at least one is MERGED, with no open branch for it (the work exists, the maintainer's step remains), else Todo; plus the label and assignment.
      - Any other issue with an open branch or open pull request belonging to it is In Progress.
      - Any other issue whose pull requests are all MERGED or CLOSED with at least one MERGED, and no open branch, is held back like step 4.1's, and listed to the maintainer with the ambiguous cases, not guessed.
      - Else Todo when the issue is listed in the pinned issue's order or has a `## Spec` or `## Agreed request` section (agreed work). An issue `../backlog/github.md` maps to the Inbox (the `idea` label, or an opening sentence saying it waits in the Inbox) goes in the Inbox, the Triage status (`../backlog/linear.md` step 2), with no type label or item shape, and step 7's comment lists it as "Inbox" beside its id. Any other issue becomes a Backlog item.
      - Ask the maintainer only for a case these rules do not settle.
   6. A pull request linked from the issue is linked from the item.
   7. After each item is created, add or update one comment on the switch item mapping GitHub issue numbers in two lists, kept apart: "Migrated" (number and item id; the pinned issue is here too, marked "order carried by creation order") and "Held back" (the issues left for the maintainer). Its first line says Linear re-serializes Markdown, so specs there match in wording, not byte for byte. An interrupted run resumes from that comment and never creates an item twice: skip an issue only when its number is already in the comment. When an item with the title this issue's item would get exists in the project and the number is not in the comment, show it to the maintainer instead of creating or skipping.
5. Closing the GitHub issues waits on the merge of the AGENTS.md pull request, and only the migrated issues and the pinned issue are closed, never the held-back ones. The switch item's wait block (step 3) carries these instructions, since a later session does not load this skill. When the maintainer says the pull request merged, or any later session finds the switch item not Done with its pull request merged (`gh pr view <N> --json state`), do what the wait block says. Its canonical command, which the block copies, for each issue under "Migrated" in the mapping comment, the pinned issue included:
   ```
   gh issue close <N> --reason "not planned" --comment "Planning for this repository moved to its backlog outside GitHub on <date>; this issue's content lives there now. Pull requests stay on GitHub."
   ```
   The comment links nothing. Then set the switch item to Done, remove its wait block and label, and clear the assignee if it is still the project's lead. From then on a pull request body here writes no `Closes #`. The held-back issues stay as they are.
6. End with one line to the maintainer saying what was set. A pending merge goes as "Ready to merge: #N" and a decision about a listed issue goes in the decision prompt (`rules.md` "What goes to the maintainer").
