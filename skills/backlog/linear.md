# Tracker: Linear

For a repository whose AGENTS.md names a Linear project, by name and team.

- Step 1: find the project with the Linear connector, by that name and team. If the connector's tools are not in the session, load them with ToolSearch (query `linear`); if they are still missing, Linear is not connected: step 1 applies.
- Step 2: statuses are Backlog (taken on, not agreed to build; parked; or holding only a decision for the maintainer; where no inbox is named, also an idea not yet taken on or kept for reference, whose opening sentence says so), Todo (agreed to build), In Progress, and Done, Canceled or Duplicate. Where the maintainer's own instructions keep a project's inbox as issues in Triage under a label they name, those issues are undecided ideas, not items: no type label, no item shape, not in the order of agreed work, and never moved with Linear's Accept, Decline or Mark as duplicate; an Intake ending other than Leave sets their status explicitly, and Leave keeps them in Triage.
- An item's type is one of the team's labels: `Bug`, `Feature` or `Improvement`.
- Step 4: on a wait, add the `Waiting on you` label and assign the item to the project's lead, so the lead's own "My issues" list shows it. No user is named. When the wait ends, remove the label and clear the assignee only if it is still the project's lead. A merge wait after "You: merge #N." gets the same label and assignment, and the same removal.
- Step 5: the next agreed work is the open Todo items without the `Waiting on you` label, ranked by Priority level name: Urgent, High, Medium, Low, then No priority, oldest created first within a level. Linear's own drag order is not used. Read every page of results before ranking, and report the waiting and In Progress items too. Claude Code sets Priority only to a level the maintainer gave: agreement alone never sets or raises it, and parking keeps it.
- Name the item's branch with its identifier as its own segment, lowercase, as in the branch names Linear itself suggests, after a Conventional Commits type, for example `feat/abc-26-branch-key`, so that Linear's GitHub integration attaches the pull request to the item. Step 6's hand-added link on the item stays, for a repository without the integration.
- Hand-made items. Off unless the maintainer's own instructions turn it on. Then, when a session lists this project to choose or plan work (not while copying a spec for a review, not for `mentat:propose`'s or `mentat:plan`'s read, and not from a skill that forbids writes), it refines each open item there that the project's lead created, that has none of the type labels, that has no `## Spec` or `## Agreed request` section and that does not carry the inbox label (step 2). First it posts a comment headed as the maintainer's original text, holding the item's title and description as they are; if that comment is refused, the item stays unchanged. Then it sets a title, one type label (`Improvement` when the choice is unclear) and a description holding the item shape's opening sentence and the original's links. A question stays a question: refining neither answers nor researches it. An item in Triage moves to Backlog; one in Todo or In Progress keeps its status and is named in the reply. The assignee and other labels stay as they are. An item that cannot get a fair title or type without inventing what it asks stays unchanged and is named in the reply.
- Waits left open. When a session lists this project to choose or plan work (not for `mentat:propose`'s or `mentat:plan`'s read, not while copying a spec for a review, and not from a skill that forbids writes), it reads each open item's wait. Merge wait: it reads, with `gh pr view` in its repository, the pull request named by each open item with a merge wait: the `Waiting on you` label and an opening sentence saying it waits on the merge of that pull request. Merged: do what `mentat:review` says after "When the maintainer says #N merged" (the wait block's steps, then the item marked done), then the repository's own post-merge steps, unless the session can establish that they already ran. Closed without merging: remove the merge wait (step 4) and leave the status. Still open, or the lookup fails: leave the item unchanged. Hand wait: for each open item with a wait block, no merge wait and no linked pull request still open, it reads the item's comments. A comment that reports the wait's `Ends when` result ends the wait (step 4: the block, the label and the lead's assignment removed). A comment that may report it, or a later report on a block with no `Ends when` line, leaves the item unchanged, and the item is named as "may be done" with the comment's date. An item whose linked pull request is still open is left unchanged for `mentat:review`, and named "may be done" the same way when a comment may report its result. Name the cleared items in one line of the reply. A skill that forbids writes instead reads both kinds of wait the same way, changes nothing, and names each item that looks done as "may be done".
- The team's labels are `Bug`, `Feature`, `Improvement` and `Waiting on you`. `mentat:setup` made them.
- A new project's overview holds only what is unique to it: its short summary is one line saying what the project is for, its long description stays empty, and its repository, where there is one, is a link under Resources.
