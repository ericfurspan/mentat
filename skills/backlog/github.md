# Tracker: GitHub issues

For a repository whose AGENTS.md names no external backlog: its GitHub issues are the backlog. Each part below maps the `SKILL.md` section it names.

- Stages, each issue in exactly one. With stage labels (`idea`, `ready`, `in progress`, `waiting`): the Inbox is an open issue labeled `idea`, Todo one labeled `ready`, In Progress one labeled `in progress`, Backlog any other open issue, and Done a closed issue; `waiting` marks a wait on the maintainer, beside the stage label, never in place of it. Without them: the Inbox is an open issue whose opening sentence says it waits in the Inbox, In Progress an open issue with a branch or pull request, Todo any other issue listed in the pinned issue's order, Backlog any other open issue, and Done a closed issue.
- Stage writes. Accept removes `idea`, or rewrites the opening sentence so it no longer says the issue waits in the Inbox, and writes the item shape's opening sentence. Committing to Todo ("Agreement"), a new issue included, adds `ready` where labels are used, appends the issue to the pinned issue's order wherever one exists, and clears any Inbox mark. Creating its branch replaces `ready` with `in progress`. When the item is done, close the issue and drop it from the pinned order: at merge, where its `Closes #` closes it, or, with manual checks after the merge (`Refs #` in its place, `mentat:pr`), once the maintainer reports each result, each failed one first filed as a follow-up; until then it stays open and waiting (its wait block, and `waiting` where labels are used).
- Item shape: the opening sentence, wait block and any open decision section, then, in place of the `Now:` and links lines, a `## Current plan` section (where the issue stands and the next step, in at most five lines, replaced in place; a longer plan goes in a comment) and a `## Decisions` section (the decisions lines of `records.md` "Decision lines", a record of more than one line adding one comment its line points to), then the spec.
- Waits on the maintainer: a step value GitHub records may not hold, such as a local path, is stated in the issue in general terms, and the messages that carry the steps carry the real command.
- Where the spec lives: the issue body's `## Spec` section, last, from its heading to the next heading of the same level or higher, subheadings included; nothing is written below it. Its body, without the heading line, is the spec.
- The order of agreed work: where the repository uses one, the pinned issue holds it, next first, without closed or parked issues. An entry whose issue waits on the maintainer points to the wait. With stage labels, the label decides the stage and the pinned issue the order: a `ready` issue missing from it ranks after the listed ones, oldest first.
- Reading an item: the maintainer is the repository's owner when the owner is a user account; read the owner's type. When the owner is an organization or cannot be read, no comment counts as the maintainer's, and the issue is still read in full. Read every page of the comments. Issues have no inline comments or resolved threads. The answer reply is one new comment holding each answered comment's `#issuecomment-` link.
- Triage outcomes. Accept: the same issue becomes the item, written as "Stage writes" says. Close: `gh issue close <N> --reason "not planned"`, with the reason in a comment. Merge: `gh issue close <N> --reason duplicate`, with a comment naming the target. Later: a dated comment; the issue stays open.
- Blocked-by links: write a link with `gh issue edit <N> --add-blocked-by <M>` and read them with `gh issue view <N> --json blockedBy`, then each blocker by the URL that read gives, with `gh issue view <url> --json state,stateReason`: done only when closed with the reason completed; closed as not planned or duplicate, the link is dead.
- When an issue closes with scope triage merged into it still not agreed, file that scope as one Inbox issue naming the closed one.
- Each issue gets one label for what it is, from the repository's own (GitHub defaults: `bug`, `enhancement`, `documentation`, `question`).
