# Tracker: GitHub issues

For a repository whose AGENTS.md names no external backlog: its GitHub issues are the backlog.

- Stages ("Stages"), each issue in exactly one. With stage labels (`idea`, `ready`, `in progress`, `waiting`): the Inbox is an open issue labeled `idea`, Todo one labeled `ready`, In Progress one labeled `in progress`, Backlog any other open issue, and Done a closed issue; `waiting` marks a wait on the maintainer and is added beside the stage label, never in place of it. Without them: the Inbox is an open issue whose opening sentence says it waits in the Inbox, In Progress an open issue with a branch or pull request, Todo any other issue listed in the pinned issue's order, Backlog any other open issue, and Done a closed issue.
- Stage writes. Accept removes `idea`, or rewrites the opening sentence so it no longer says the issue waits in the Inbox, and writes the item shape's opening sentence (where the work came from). Committing to Todo ("Agreement"), a new issue included, adds `ready` where labels are used and appends the issue to the pinned issue's order wherever one exists, and clears any Inbox mark. Creating its branch replaces `ready` with `in progress` where labels are used. When its pull request merges, close the issue and drop it from the pinned issue's order.
- The tracker's order ("The order of agreed work"): where the repository uses one, the pinned issue holds the order of agreed work, next first, without closed or parked issues. An entry whose issue waits on the maintainer points to the wait. With stage labels, the label decides the stage and the pinned issue the order: a `ready` issue missing from it ranks after the listed ones, oldest first.
- The Backlog order, for the lookup of the next-work offer (`next-work.md`): Backlog issues oldest first, parked ones left out, reading every page of issues before choosing.
- Reading an item (`item-reads.md`): the maintainer is the repository's owner when the owner is a user account; read the owner's type. When the owner is an organization or cannot be read, no comment counts as the maintainer's, and the issue is still read in full. Read every page of the issue's comments. Issues have no inline comments or resolved threads. The answer reply is one new comment on the issue holding each answered comment's `#issuecomment-` link.
- Triage outcomes. Accept: the same issue becomes the item, written as "Stage writes" says. Close: `gh issue close <N> --reason "not planned"`, with the reason in a comment. Merge: `gh issue close <N> --reason duplicate`, with a comment naming the target. Later: a dated comment; the issue stays open.
- Start waits (`start-waits.md`): an `<item id>` is the issue's `#<N>`, done only when closed with the reason completed (`gh issue view <N> --json state,stateReason`); closed as not planned or duplicate, the wait is dead.
- An issue Claude Code files or the maintainer agrees opens with one sentence saying where the work came from, in the terms of the item shape's first bullet.
- When an issue closes with scope triage merged into it still not agreed, file that scope as its own issue, in Backlog, linking the closed one.
- Each issue gets one label for what it is, from the repository's own (GitHub defaults: `bug`, `enhancement`, `documentation`, `question`).
