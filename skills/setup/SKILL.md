---
name: setup
description: "Shows and sets Mentat's per-repository settings (the backlog, the test command and the Code Review Rules), which live as prose in the repository's AGENTS.md, including moving a repository's planning from GitHub issues to a Linear project. Started by the maintainer."
disable-model-invocation: true
---

The maintainer wants to see or change this repository's Mentat settings. They live as prose in the repository's AGENTS.md. There is no config file, and this skill adds none. This runs once: do it, then normal work resumes. If the maintainer typed text after the command, start from that.

1. Read every AGENTS.md that applies (root and nested, and `AGENTS.override.md` if present, which replaces the AGENTS.md beside it). Show the three effective settings in the form `rules.md` uses at session start: the backlog (the named external one, else GitHub issues), the test command AGENTS.md names or "not named", and whether a Code Review Rules section exists. Show effective values, never "default". Change nothing yet.
2. Ask only about what is missing or would change, one decision at a time with a recommendation, as `rules.md` "How it reaches them" says. When the maintainer typed what to change, do that. When they typed nothing, ask once which of the three settings to change, naming the missing ones first, with a recommendation. "None" ends the skill: no pull request.
3. The three settings, and the exact lines written to AGENTS.md. A line written replaces the existing sentence for that setting, never sits beside it. When the choice is GitHub issues, the existing backlog sentence is deleted and nothing is written:
   - Backlog: GitHub issues (nothing written) or a Linear project in a named team. Line: ``The external backlog is the Linear project `<name>`, in team `<team>`.`` Recommend the repository's name as the project name.
   - Test command: the one AGENTS.md names, else the one the repository shows. Confirm it with the maintainer and write it only on a yes (`rules.md` adds none unasked). Line: ``The one test command is `<command>`.``
   - Code Review Rules: only when the section is missing; an existing section is the maintainer's and changes only if they ask. Offer this starter under a `## Code Review Rules` heading, for the maintainer to trim:
     - Flag any secret, token or credential added to the repository, including in tests, fixtures and workflow files. Placeholder values that are clearly fake are fine.
     - Flag workflow changes that give a job secrets, write permissions or deploy access it does not need. Workflows should declare `permissions` explicitly and pin third-party actions to a commit SHA.
     - Flag shell scripts that break on paths with spaces or ignore a failing command.
     - Flag only problems with a realistic trigger.
4. Write the lines in one pull request, by the normal path. The maintainer's answers above are the agreement, so the change is not weighed again. The main session edits no files.
   - Put the spec (shape in `mentat:pr`) in the repository's backlog item: a GitHub issue when the backlog stays GitHub issues, an item in the external backlog when it already has one, or the switch item (step 5) when switching to Linear. Requirements are numbered: the lines in AGENTS.md, and, when switching, the migration and the closes. "Out of scope:" is last.
   - Run `mentat check`. Brief the `builder` subagent: the lines, the AGENTS.md file to edit (the root one; the override if present), the file's own style, that each line replaces the existing sentence for that setting (and that a backlog sentence is deleted when the choice is GitHub issues), and to leave the rest alone. Run the repository's test command on a clean tree before the push, call the Skill tool with `mentat:pr` for the body and with `mentat:review` for the loop.
   - When switching, the pull request reads its spec from the switch item, and every review is `mentat review --request <file> <N>` (and `--grok`), since AGENTS.md names the backlog only once the pull request merges. The pull request body writes no `Closes #`.
5. Linear, when chosen. Load the Linear connector tools with ToolSearch (query `linear`). If they are missing, Linear is not connected: say so and stop; nothing has been created. Then, in order:
   - Find the team by name. If it is not there, stop and say so.
   - If a project of the chosen name exists in the team, stop and show it to the maintainer.
   - Create the project with the description in `mentat:backlog` ("Tracker: Linear", new project description), the repository's name filled in, and the maintainer as lead.
   - Create the switch item first: title `Move planning from GitHub issues to this backlog`, label Improvement, status Todo, an opening sentence, and a `## Spec` holding the AGENTS.md line, the migration and the closes, in public-safe words that name neither the workspace nor an item. Say the closes happen after the pull request merges, so the pre-merge review reads them as a post-merge step, not something the diff must contain. Set it In Progress when the branch exists.
   - Migrate the open issues (step 6). When the pull request is open, add the `Waiting on you` label and the lead's assignment (`mentat:backlog` Linear step 4) and the wait block to the switch item. A later session never loads this skill, so the block is self-contained: the heading "## Waits on the maintainer"; the pull request number; the issue numbers to close (the migrated issues and the pinned issue, not the held-back ones); the exact `gh issue close` command with the fixed comment, as in step 7; and the steps: merge the pull request, then, only once `gh pr view <N> --json state` reports merged, run the command for each listed issue, set the switch item to Done, remove the block and the label, clear the assignee if it is still the project's lead, and drop the item from the project's order.
6. Migration. One open GitHub issue at a time, from the main session (the builder never touches the backlog). The pinned issue is not migrated as an item: only its order is carried to the project, and it is closed in step 7 with the others.
   1. List the open issues. For each open issue, ask GitHub which pull requests close it (the owner and repository from `gh repo view --json nameWithOwner`):
      ```
      gh api graphql -f query='{ repository(owner:"<owner>", name:"<repo>") { issue(number:<N>) { closedByPullRequestsReferences(first:50, includeClosedPrs:true) { nodes { number state } } } } }'
      ```
      The query is per issue and complete: it returns every pull request GitHub links as closing the issue (GitHub's own reading of close, fix and resolve keywords), with `state` OPEN, MERGED or CLOSED. An issue with any OPEN node is still closed by an open pull request: it is not migrated and is held back. List those to the maintainer in one message, recommending they stay on GitHub until that pull request merges. Do not close them.
   2. Read the issue: `gh issue view <N> --json title,body,labels,state`.
   3. The spec is the issue's `## Spec` section, else its `## Agreed request`, heading kept, copied without rewording (pass the text through, never retype it). The item follows the item shape in `mentat:backlog`: an opening sentence in Claude Code's words; the issue's `## Waits on the maintainer` section first when it has one, with the `Waiting on you` label and the lead's assignment (`mentat:backlog` Linear step 4); the spec; `## Current plan` when the issue has one. Anything else in the body goes in the item's first comment, unchanged, labeled as copied from GitHub issue #N. The issue's own comments stay on the issue.
   4. Type from the label: `bug` is Bug, `enhancement` is Feature, else Improvement.
   5. Status. With stage labels: `idea` is Backlog, `ready` is Todo, `in progress` is In Progress, `waiting` is the status of a waiting issue (below), plus the `Waiting on you` label and the lead's assignment (`mentat:backlog` Linear step 4). Without them, find the branches (`git ls-remote --heads origin`) and use the pull requests step 6.1's query returned. A branch belongs to the issue only when: the issue number is its own segment of a branch's name, set off by `/`, `-`, `_` or an end (`feat/10-globe`, `issue-10`, `10-globe`), not part of a longer number or a date, or the issue body names the branch. A pull request belongs to the issue only through that query. Any other resemblance does not count; when a branch might belong but does not meet this rule, the issue is held back like step 6.1's and listed to the maintainer with the ambiguous cases, not marked In Progress. Then:
      - An issue with a `## Waits on the maintainer` section is agreed work. It is In Progress when an open branch or open pull request belongs to it, or every pull request in the query is MERGED or CLOSED and at least one is MERGED, with no open branch for it (the work exists, the maintainer's step remains), else Todo; plus the label and assignment.
      - Any other issue with an open branch or open pull request belonging to it is In Progress.
      - Any other issue whose pull requests are all MERGED or CLOSED with at least one MERGED, and no open branch, is held back like step 6.1's, and listed to the maintainer with the ambiguous cases, not guessed.
      - Else Todo when the issue is listed in the pinned issue's order or has a `## Spec` or `## Agreed request` section (agreed work); Backlog only with none of these.
      - Ask the maintainer only for a case these rules do not settle.
   6. A pull request linked from the issue is linked from the item.
   7. After each item is created, add or update one comment on the switch item mapping GitHub issue numbers in two lists, kept apart: "Migrated" (number and item id; the pinned issue is here too, marked "order carried") and "Held back" (the issues left for the maintainer). Its first line says Linear re-serializes Markdown, so specs there match in wording, not byte for byte. An interrupted run resumes from that comment and never creates an item twice: skip an issue only when its number is already in the comment. When an item with the title this issue's item would get exists in the project and the number is not in the comment, show it to the maintainer instead of creating or skipping.
   8. When all are done, set the project's order of agreed work (`mentat:backlog` step 5): the switch item first, then the migrated In Progress and Todo items in the pinned issue's order, else by issue number. Replace "Nothing agreed is waiting." in the project description.
7. Closing the GitHub issues waits on the merge of the AGENTS.md pull request, and only the migrated issues and the pinned issue are closed, never the held-back ones. The switch item's wait block (step 5) carries these instructions, since a later session does not load this skill. When the maintainer says the pull request merged, or any later session finds the switch item not Done with its pull request merged (`gh pr view <N> --json state`), do what the wait block says. Its canonical command, which the block copies, for each issue under "Migrated" in the mapping comment, the pinned issue included:
   ```
   gh issue close <N> --reason "not planned" --comment "Planning for this repository moved to its backlog outside GitHub on <date>; this issue's content lives there now. Pull requests stay on GitHub."
   ```
   The comment links nothing. Then set the switch item to Done, remove its wait block and label, clear the assignee if it is still the project's lead, and drop it from the project's order. From then on a pull request body here writes no `Closes #`. The held-back issues stay as they are.
8. End with one line to the maintainer: what was set, and what waits on them (the merge, a decision about a listed issue, or nothing).
